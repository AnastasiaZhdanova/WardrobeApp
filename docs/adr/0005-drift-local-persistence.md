# 0005. drift for local persistence, seeded once, with no sync yet

Status: Accepted

## Context
The wardrobe must be browsable without a network, review decisions must
survive a restart, and there is no backend. The data is relational and small (tens
to hundreds of items).

## Decision
- drift (SQLite) via `drift_flutter`, one database
  (`lib/core/db/app_database.dart`) with two tables, `WardrobeItems` and
  `ReviewedOutfits`. Schema version 2; `onUpgrade` creates the reviews
  table for databases from version 1.
- `DriftWardrobeRepository` reads only from local persistence (drift).
  If the table is empty, it is filled once from `seedWardrobe`, which
  stands in for a remote source. Concurrent first reads share one seeding
  future; a failed seed is retried on the next read.
- Enums are stored as their names, and seasons as a comma-separated
  string. An unknown name throws `ArgumentError`, which is treated as a
  programming error, not a user-facing failure.
- Item images are bundled assets (`assets/wardrobe/`), generated by
  `tool/generate_wardrobe_art.dart`. `WardrobeImage` decodes them at
  display size (`cacheWidth`).
- Tests use `NativeDatabase.memory()` for the drift repositories and
  in-memory fakes for widget tests.

## Alternatives considered
- **Hive / Isar:** fast key-value or object storage, but weaker querying,
  and Isar's maintenance status is uncertain.
- **shared_preferences + JSON:** enough for a list, not for review
  history or later filtering in SQL.
- **sqflite directly:** no type-safe queries or generated migrations.
- **Seeding in `MigrationStrategy.onCreate`:** couples the schema to mock
  data.

## Consequences
Positive:
- Works without a network. Type-safe queries and a migration path exist from day
  one.
- Review decisions persist, and the review queue is a live stream.

Negative:
- **No sync and no invalidation.** Local persistence is seeded once, so changes
  to `seedWardrobe` never reach an existing install unless the app data is
  cleared.
- Filtering happens in memory on the full list (`filteredWardrobeProvider`),
  not in SQL. That's fine at this size but won't scale to thousands of items.
- The wardrobe list is read once, not watched, so it doesn't update live.
- The database is not encrypted (see ADR 0006).
- Image decoding at display size is applied, but nothing was measured
  with DevTools.
- There are no schema-dump migration tests.

## What I would change at production scale
Add a remote source with delta sync (`updatedAt` / ETag) and conflict
rules for review decisions. Move filters into SQL with indexes, use drift
`watch()` for the wardrobe, and encrypt the database (SQLCipher). Load
images from a CDN with sized thumbnails and a disk cache, and add drift
migration tests from exported schemas.
